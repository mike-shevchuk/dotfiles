# /night-audit — нічний аудит змердженого (Mike 18.11: «перевірить /merged за цей спринт і зробить нічний аудит, саботаж і жорстку перевірку, щоб детально знайти проблеми, слабкі місця або оптимізацію»)

Чат українською, терміни англійською. Усе з живих джерел, не з пам'яті.

## ✅ Що можна / ⛔ що не можна (Mike 18.11: «може переключати деплої, створювати train і тестувати; не можна лише мерджити, а все решту з /pr-state може робити»)
- ✅ **Можна все з воріт `/pr-state`:** збирати train-гілки (`train-w<N>-<k>` від origin/main + PR-гілки), деплоїти їх на dev (`gh workflow run 165841775 --ref <train>`), перемикати dev між train / main, перемикати workflow engine (`cd ~/code/b2b/workflow-engine && just wf-engine-switch-dev`), ганяти проби, саботаж, PRE, JT; `/code-review high`, `/ponytail-review`, стампи `pipeline-stamp.sh`; `jb2b pull-main` + push у ВІДКРИТІ PR-гілки (merge, не rebase); фікси знахідок — у нову гілку + новий PR (EN, `## PROD steps`, без Co-Authored-By); JT-коментарі англійською на PR.
- ⛔ **Не можна:** `gh pr merge` / будь-який merge у main, push у main, prod (деплой prod іде лише через merge/release), force-push, видалення гілок, записи в Linear (лише чернетки).
- Конфлікт при збиранні train → PR не включати, `git merge --abort`, знахідка «конфлікт <PR> × <PR>» у звіт; гарячий шлях 911/emergency сам не резолвити.
- Після аудиту dev лишити на **останньому train або main** (не на гілці з саботажем) і записати це в звіт.

## ⏰ Межа часу — до 03:00 (Mike 18.11: «запускати це я буду сам, а працювати буде до 3 ночі»)
- Запускає лише Mike вручну (`/loop /night-audit`, див. 🔁), ніякого розкладу/cron.
- Робота триває до **03:00 за місцевим часом**. Перед КОЖНИМ PR і кожним прогоном на dev — `date +%H:%M`; якщо вже ≥ 02:45 — нових PR не починати, поточний дограти або зупинити з прибиранням (undo, fixture 0 alerts), і одразу писати звіт (крок 4) з тим, що встигли.
- У звіті окремий блок «⏰ Не встигли до 03:00»: які PR / кроки лишились, щоб наступний запуск почав з них (аргумент `PR# …`).
- Порядок, щоб найважливіше встигло: спершу PR з найвищим 🎯 (`w<N>/priorities.tsv`) і ті, що чіпають emergency / 911 / notify; дрібні — в кінці.

## 🔁 Цикл до готовності, як Ralph loop (Mike 18.11: «має бути щось схоже з ральф луп для night-audit»)
- Запуск: **`/loop /night-audit`** — без інтервалу, вбудований `/loop` сам задає темп. Одиночний `/night-audit` теж працює: це одна ітерація.
- **Стан — лише у файлі**, не в пам'яті: `~/.claude/fleet-board/w<N>/night-audit-state.tsv` (`#` · `🎯` · `item` (PR# або PUN) · `kind` audit|push · `step` · `status` todo|doing|done|skip|blocked · `note` · `HH:MM`). Кожна ітерація починає з `date +%H:%M` і читання цього файлу.
- **Ітерація:**
  - файлу нема → кроки 1 + 2½ → записати чергу за 🎯 спаданням (усі `todo`);
  - є рядок `doing` → дограти або прибрати (undo, fixture 0 alerts);
  - далі взяти перший `todo` і зробити ОДИН крок (рев'ю PR, прогін, саботаж або наступне ворото) → оновити рядок і `note` → кінець ітерації.
- **Темп (ScheduleWakeup):** чекаєш deploy, train або вікно-власника → 600–900 с; щойно закрив крок і далі є `todo` → 60 с.
- **Стоп:** час ≥ 02:45 АБО нема `todo`/`doing` → крок 4 (звіт) + 5 → `ScheduleWakeup stop: true`. Як і в Ralph: не зупиняти цикл раніше «бо застряг». Застряглий пункт → `blocked` з причиною, і далі наступний.
- Скасувати вручну: Mike пише що-небудь у вікно або Esc.

## 📊 Прогресбар і прогноз — у КОЖНІЙ відповіді (Mike 20.11: «давай в /night-audit прогресбар та предікт час»)
- Після кожної ітерації і в кожній відповіді Mike першим рядком: `~/.claude/fleet-board/bin/night-progress.sh` → `🌙 night-audit ▓▓▓▓░░ k/N (x%) · зараз: <пункт · крок> · ≈HH:MM (ще ≈M хв)`. Прогноз = зараз + відкриті пункти × середні хв на закритий (з колонки `HH:MM`), годинник, не відносний час.
- Крок 3 (прогони на dev) — окремий рядок з тим самим форматом: `🧪 крок 3 ▓▓░░ r/R рецептів · зараз <рецепт> чесний|саботаж · ≈HH:MM` (≈2 хв на прогін; ліміт SES/dev — у дужках).
- Колонку `HH:MM` оновлювати при КОЖНІЙ зміні `status` — інакше прогноз бреше.
- **`/eta-wake` ON на весь аудит:** на старті `touch ~/.claude/fleet-board/w<N>/eta-wake.on`; поки є `todo`/`doing` — не вимикати. Останній рядок кожної відповіді — `😴 Ти спиш до ≈HH:MM` з `night-progress.sh`.
- **Прогноз = обіцянка з перевіркою (Mike 20.11: «якщо даєш прогнози, то в тій годині оновлюй дані»).** Після кожного прогнозу запусти фоном `~/.claude/fleet-board/bin/eta-wake.sh` (`run_in_background`): він спить до найближчого `≈HH:MM` у `tracks.tsv` і, закінчившись, будить ліда. На пробудженні: `night-progress.sh` → для кожного due-треку звірити факт (вікно, dev-queue, гейти) → `track.sh` з новим статусом/ETA або `done` → знову `eta-wake.sh`. Зірваний ETA — сказати Mike причину і нову годину.
- Той самий скрипт дописує **👥 флот** (Mike 20.11: «задачі що виконуються і плануються, скільки агентів працюють і стан кожного коло прогресбару»): лічильник 🔄/🚂/🙋/🧭/💤 і рядок на вікно — задача · стан · бар · крок · ETA. Джерело — `lead.py footer` (не дублювати). ETA вікна = 6-те поле `track.sh <week> "<track>" "<step>" <status> <pct> "≈HH:MM …"` — ставити годинник при кожному кроці.

## 2. Жорстке рев'ю кожного PR (субагенти, ПО ОДНОМУ — RAM)
Для кожного PR — Agent `model: "sonnet"` з брифом (≤15 рядків звіту):
- `gh pr view <N> --json title,body,mergeCommit,files` + `git show <mergeCommit> --stat` + diff лише змінених файлів (частинами).
- Шукати (кожен пункт — `file:line` на **origin/main**, не на гілці): помилкові шляхи й retry (SQS `batchItemFailures` + `reportBatchItemFailures`), ідемпотентність і дублі, гонки, authz/IDOR по всіх порталах, scan замість query, N+1 / послідовні виклики в гарячому шляху emergency (p95 < 3 s), тиха втрата даних (except → None), `os.environ[...]` у construction graph, CloudWatch period, TTL, логи (ERROR лише для справжніх помилок), дві джерела правди, вартість AWS.
- Кожна знахідка: **бал 0–100** (серйозність), сценарій «вхід → що зламається», фікс одним рядком, розмір зміни.
- Оптимізація окремо: що можна прибрати / прискорити / здешевити, з оцінкою виграшу.
Без поверхневих «ok»: якщо знахідок нема — субагент пише, що саме перевірив і чому певен.
- **Guru за потреби (Mike 18.11: «при потребі запитуй у guru»):** сумнів у балі ≥ 50, лід змінює бал субагента, знахідка чіпає відкритий PR або архітектуру (порядок, ідемпотентність, PC/вартість) → питання в 🧙 guru-вікно (`fleet.json`/`pr-windows`: роль guru) через `send.sh "NIGHT: …"`. У питанні: file:line, сценарій, конкретне питання. Чекати «🙋 LEAD: GURU done», вердикт guru — у звіт поруч зі знахідкою. Дрібне не носити.

## 3. Саботаж і регресії на dev (послідовно, з прибиранням)
Для кожного PR з рецептом проби (`w*/preflight-map.tsv` → `jb2b <topic>-try`):
1. **Чесний прогін** `DEMO_OPERATOR=agent DEMO_BROWSER=0 jb2b <topic>-try yes=1 cleanup=1` → вердикт має бути `гейтів: ✅ N … з N`, у відкаті нема «не відкотилось». Не так → **регресія** (найчастіше — сусідній merge зламав): бал ≥ 80.
2. **Саботаж** `<TOPIC>_SABOTAGE=1 jb2b <topic>-try yes=1 cleanup=1` (змінна — у шапці рецепта: `# Lint/ sabotage: …`) → проба **мусить** впасти на своєму кроці. Не впала → проба нічого не доводить: бал ≥ 70, фікс рецепта.
3. Рецепт без sabotage-режиму → знахідка «проба без саботажу» (бал 50) + пропозиція, яку одну лінію коду перевернути.
4. Імовірнісні кроки → 3 прогони поспіль; нестабільний крок = знахідка.
Квота SES / throttle на dev → позначити «не доведено (середовище)», не рахувати провалом коду.
